# Debug: Soloist Browse Audio Stutter

## Symptoms

- **Expected:** Smooth continuous audio playback when browsing/playing tracks via SpotOn OPML menus (Soloist backend)
- **Actual:** Audio starts delayed, stutter gets progressively worse, ~5s silence gap, repeats cyclically
- **Errors:** No explicit errors in logs — audio simply stutters
- **Timeline:** Never worked — Soloist Browse-Playback was never live-tested (Phase 73 Windows 1-4 all `PRESENT_BEHAVIOR_UNVERIFIED`)
- **Reproduction:** Play any album/track via SpotOn Browse menu with backend=soloist. Stutter appears within 10-20 seconds.

## Current Focus

  hypothesis: "Soloist writes an initial burst of audio (~1.02s, 44 x 8192-byte pa_stream_write() calls = 360448 bytes) into the ring, the ring drains to fill=0 (genuine PulseAudio underrun condition) as the client (squeezelite/curl) consumes it in real time, and Soloist then PERMANENTLY stops calling pa_stream_write() because it is waiting for the underflow_cb (registered via pa_stream_set_underflow_callback) to fire before feeding more audio — a callback fake-libpulse.c never invokes (the doc comment on pa_stream_set_underflow_callback explicitly flags this as a known, deliberate gap: 'this stub NEVER invokes underflow_cb anywhere'). **Conclusion:** the underflow_cb fix is real, correctly implemented, and verified working exactly as designed (confirmed via direct log evidence across 4+ independent invocations) -- it is a genuine improvement in PA-API fidelity that should be kept. However, it does **not** resolve the reported Browse stutter symptom, because Soloist's writer is not actually gated on this signal for resuming after the ring drains -- the deeper blocker is Soloist being unable to reliably fetch/decode further track audio at all, most likely due to Spotify-side audio-key/CDN throttling accumulated from the very large volume of rapid play/flush cycles this debugging session (and the prior one) generated against the same test account within a short window. This is outside fake-libpulse's/SpotOn's control and cannot be resolved by further code changes from this repo; it requires either a genuine account cooldown (duration unconfirmed -- 90s was insufficient in this session) or re-testing on a less-throttled session to determine whether the underflow_cb fix alone is sufficient once the account-level condition clears.

### Root-Cause Hypotheses

**A) Ring-Buffer Rate-Mismatch (PRIMARY)**
- Ring: `RING_BYTES_PER_SEC = 44100 * 4 * 2 = 352800 B/s` (S32LE)
- HTTP-Thread polls every 50ms, chunk size 16384
- Per tick: 352800 * 0.05 = 17640 bytes in, 16384 bytes out → 1.2 KB/tick deficit?
- Ring capacity: 20s (7 MB) — deficit accumulates over minutes to overflow → drop-oldest → gap

**B) HTTP Backpressure**
- `_http_write_all()` has 2s poll-timeout per chunk
- If squeezelite reads slowly (player buffer full), backpressure → ring fills up
- Periodic emptying when buffer has room → burst → briefly smooth → full again

**C) Soloist Decoder Timing**
- Soloist writes Float32 via `pa_stream_write()` in bursts, not evenly
- Ring fill level fluctuates → HTTP thread sometimes has data, sometimes not → stutter

**D) squeezelite Buffer-Underrun**
- If HTTP stream delivers unevenly → squeezelite buffer empties → underrun
