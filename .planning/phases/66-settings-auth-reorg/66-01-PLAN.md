<objective>
Revert the 65-04 one-step Keymaster auth to the two-step architecture: PKCE with the ncspot Extended Quota Client ID for Web API tokens (step 1), ZeroConf pairing as the REQUIRED source of playback credentials (step 2). The Keymaster client_id (65b70807-prefixed) caused severe 429 rate limiting because it shares one global rate-limit bucket with every librespot and Spotify Desktop user; the ncspot ID (d420a117-prefixed) has its own Extended Quota bucket, so /me and all Web API calls work again without the 65-05-session workarounds. Those uncommitted workarounds (temp accounts, /me retry loop, undefined error helper) are reverted wholesale — they patched a symptom this plan removes at the source.

Phase 66 decisions (user direction 2026-08-15, supersedes the 65-04 amendment of phase-65 D-02):
- D-01: PKCE default client_id = SPOTON_DEFAULT_CLIENT_ID (ncspot Extended Quota, `d420a117a32841c2b3474932e49fb54b`); KEYMASTER_CLIENT_ID retired as PKCE default.
- D-02: No playback-credential auto-derivation from account PKCE tokens (wrong provenance for Login5, per 65-05 hypothesis result); ZeroConf pairing (65-02) is the REQUIRED playback step — auth is two steps again.
- D-03: The Keymaster browser fallback (65-03, Docker/VLANs without mDNS) keeps KEYMASTER_CLIENT_ID + scope=streaming for credential derivation only — must continue to work unchanged.
- D-04: The uncommitted 65-05 UAT-session workarounds in Settings.pm and Credentials.pm (temp accounts, pending resolution, /me retry, JWT-decode attempts) are fully reverted — clean code, no partial keeps.

Purpose: Eliminate the 429 blockade at its source and restore a clean, honest auth model.
Output: ncspot-default PKCE flow with no derivation tail, reverted workarounds, ncspot refresh fallback, updated regression gates.
</objective>
