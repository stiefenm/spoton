<objective>
Move soloist Browse playback from Phase 72's per-track `--single-track` spawning onto the persistent daemon (D-03, Modell B from RESEARCH Pattern 6): LMS keeps its real playlist; Soloist plays via WS `play {uri}`; the next LMS Spotify track is seeded via `add_to_queue`; Soloist's own `track_changed` drives the LMS playlist index forward; audio flows continuously from `/stream` with takeover reconnects at boundaries. Seek returns (WS `seek`), pause/stop are forwarded, sync groups proxy. An empirical Wave-0 spike (mandatory per RESEARCH) settles track-end/autoplay/queue-echo behavior BEFORE the advance logic is frozen.

Purpose: this is what the persistent daemon exists for — the data-dir lock problem (skipped/early-switched tracks) disappears structurally, and the gapless-capable audio path opens.
Output: spike protocol, daemon-based Browse in ProtocolHandler/SoloistWS/Connect.pm, rewritten t/29.
</objective>

**1. SoloistWS browse session state machine:**
- Fields: browseSession (0/1), browseCurrentUri, browseSeededUri, browseAdvancePending.

- **Seeding:** on every `position_sync` while browseSession: compute remaining = duration (from the LMS song via the daemon's client) minus position; when remaining < 15 s and no seed sent for this track: look up the client's NEXT playlist entry URL; if it matches `^spoton://(track|episode):([A-Za-z0-9]+)$` → `add_to_queue { uri => "spotify:$1:$2" }`, record browseSeededUri; anything else (radio, local, end of playlist) → no seed (Soloist will stop at track end per the Task-1 finding; the stop event lets LMS advance normally — the mixed-playlist boundary).
