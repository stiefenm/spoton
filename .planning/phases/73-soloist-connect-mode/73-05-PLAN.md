## Diagnosis evidence (from /var/log/squeezeboxserver/server.log, UAT session 2026-08-27 08:20-08:52, and a live WS probe)

**Gap 2 (seek):** The seek WAS dispatched (log 08:38:20 shows the seek command sent
and acknowledged as ok at the Connect.pm level), but the daemon replied:
`daemon reported error (last command 'seek'): invalid JSON or missing required fields`.
Root cause (reproduced offline with the LMS-bundled JSON::XS 2.34): `_bufferedSeek`
interpolates `$positionMs` into its DIAG log line before passing it on; the
stringification caches a PV on the SV, and JSON::XS then serializes the dualvar as
`"position_ms":"145791"` (a JSON string). The daemon requires a numeric field
(binary string: `seek requires an explicit non-negative position_ms`). The volume
command works only because Connect.pm happens to wrap it in a fresh `int()`. The
browse-seek path (`_bufferedBrowseSeek` → `sendCommand('seek', ...)`) has the
identical latent bug.

**Gap 1 (resume at 0):** Every logged resume emission carries `position=0.000`
because `lastPositionMs` is never updated: ALL `playback_state` frames containing
non-ASCII item metadata fail decode with `malformed UTF-8 character in JSON string
... offset ~1026 ... before "posit...`. Root cause: the vendored
`Protocol::WebSocket::Client::read` dispatches `$frame_buffer->next` (Frame.pm line
92-98), which returns `Encode::decode('UTF-8', $bytes)` — a decoded CHARACTER
string — while `from_json` (= `JSON::XS::decode_json` via VersionOneAndTwo) expects
UTF-8 OCTETS. A live probe confirmed: `decode_json` fails on these frames while a
character-mode `JSON::XS->new->decode` parses them perfectly. The probe also
confirmed the playback_state position shape: `position => { position_ms => 6112,
speed => 0, timestamp_ms => ... }` and that the daemon pushes playback_state
snapshots on transitions (including while paused) — so once decoding works, the
pause position is always in the baseline at resume time.

**Spurious resume emissions:** `_onPlaybackChanged` emits 'resume' for EVERY
'playing' status, including the buffering→playing sequence after each track change
(log: resume with position=0.000 within 60ms of every 'change'), and logs
'buffering' as an unrecognized status. A resume must only be emitted for a real
Paused→Playing transition.
