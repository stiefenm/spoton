<objective>
GH #135: surface the Spotify Connect queue ("Up Next") in LMS via an on-demand OPML feed backed by `GET /me/player/queue`.

Purpose: Cluster 4, D-01 full scope. Implementation choice (Claude's discretion per CONTEXT.md, documented for the record): the issue offers Option A (Web API) vs Option B (Spirc events via two librespot cherry-picks + a structured Rust→Perl channel). This plan ships Option A in its rate-safe shape — ON-DEMAND ONLY, one request per menu open, never polled — which sidesteps the issue author's own rate-pool objection to polling (the objection targets recurring calls; a menu-open fetch is user-initiated and single). Option B remains a compatible future layering (event-driven refresh of the same feed, librespot-only) and is NOT undone by this work; it stays available for Phase 77+. This choice works for BOTH backends (the Web API queue reflects the account's active session regardless of which local daemon hosts it), which Option B does not.

Output: Client.pm getQueue, Plugin.pm Up Next feed + menu wiring, i18n strings, tests.
</objective>
