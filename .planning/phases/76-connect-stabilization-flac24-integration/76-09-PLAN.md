<objective>
Fix RC-1 of the Soloist Browse audio stutter (debug session `.planning/debug/soloist-browse-stutter.md`): the Pitfall-4 "unexpected uri" classification in `SoloistWS::_onBrowseTrackChanged` fires even when the announced URI equals the URI LMS itself asked Soloist to play.

Mechanism (from live log evidence): `startBrowseTrack($uri)` sends `play {uri}` (SoloistWS.pm §992) and sets `browseCurrentUri` (§979) — but leaves `browseSeededUri` undef (§980). When Soloist then announces exactly that track via `track_changed`, `_onBrowseTrackChanged` (§661-724) only recognizes a **seeded** match (§674-699). The confirmation of our own play command falls through to the Pitfall-4 branch (§700-723):

- Multi-entry queue (§708-716): logs `browse track_changed unexpected uri X (expected X) -- correcting` and re-sends `play` for the SAME track — a flush/restart of audio that was starting correctly, feeding the cyclic stutter.
- Single-entry queue (§717-723): calls `endBrowseSession('queue_end')` which sends `pause` (§1030, not in `%_BROWSE_END_SKIP_PAUSE` §1013) — audio stops ~1s after track start.

Purpose: eliminate the false positive so Browse playback of any queue length survives its own play confirmation, while keeping every genuine Pitfall-4 defense (autoplay/drift correction, no free-running queue) intact.

Output: equality branch in `_onBrowseTrackChanged` + unit tests in the existing t/31 harness that fail against the current code and pass after the fix.
</objective>
