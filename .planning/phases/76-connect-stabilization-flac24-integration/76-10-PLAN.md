<objective>
Fix RC-2 of the Soloist Browse audio stutter (debug session `.planning/debug/soloist-browse-stutter.md`, evidence entries 20:09-20:11): after a daemon restart, Soloist restores the previous Spotify session and re-announces it; Connect.pm's Phase-76 restart gate correctly suppresses the auto-play — but leaves a stale, hijack-capable ownership claim behind. The next user-initiated Browse play is then partially intercepted by Connect handlers.

Three concrete defects combine into the hijack:

1. **pendingConnect leak:** `_connectEvent` sets `pendingConnect => 1` synchronously on every 'start' (§827) — but the restart-gate suppressed branch (§1110-1128) returns without ever clearing it (the normal path clears at §1185, the resume path at §1024). The 'change' (§1208) and 'seek' handlers' `|| pendingConnect` exceptions then treat the dormant session as a live pending start indefinitely (metadata-bleed vector, KE connect-metadata-bleed).
2. **Unreachable stale-claim release:** in `_onNewSong` (§438), the first branch `if (isSpotifyConnect($client)) { ...; return; }` (§468-492) and the release block `if ($_activeConnectPlayer && $_activeConnectPlayer eq $client->id)` (§494-515) test the IDENTICAL condition (`isSpotifyConnect` §99-106 is exactly that comparison) — the release code that would clear the claim when a non-Connect song starts can never execute. The resume handler's own comment (§935-937) says "only _onNewSong clears it" — i.e. today nothing ever does.
3. **_onPause hijack window:** a Browse `playlist play` internally stops/pauses the previous state BEFORE `getNextTrack` arms `browseSession`, so `_soloistBrowseWs` (§173-186) returns undef and `_onPause` falls through to `isSpotifyConnect` (§591) → true via the dormant claim → `_sendControlCommand($client, '/control/pause')` (§654), which for a SoloistDaemon maps to a WS `pause` (§282-291) — pausing the very session the Browse play is trying to start.

Purpose: make a dormant restored Connect session cleanly yield to an explicit user Browse action, while preserving the restart gate's design intent (session stays visible and manually resumable from the app via the 'resume' re-entry path §962-1028, which does NOT depend on the ownership claim).

Output: three surgical fixes in Connect.pm + grep-gate regression pins in t/37_connect_lifecycle.t.
</objective>
